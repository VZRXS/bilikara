# v0.9 design audit and approved exceptions

These rules record the approved design reference order and product exceptions.
Advisory references do not authorize appearance, gesture or framework changes.

## Reference order and evidence

Use Apple HIG, then Microsoft Fluent/Windows Design, then Google
Material/Android guidance to resolve advisory choices. Explicit product decisions,
actual capabilities and accessibility/safety requirements retain precedence.
Classify a finding as CONFLICT, ADVISORY, PRODUCT EXCEPTION,
ACCESSIBILITY/SAFETY GATE or DEVICE-UNVERIFIED; do not turn a style preference
into a cross-platform prohibition.

Official design references:

| Source | Relevant guidance / scope |
| --- | --- |
| [Apple accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) and [buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) | Review effective hit regions and accessibility separately from visible shapes; retain the product's 44pt iOS target review gate. |
| [Apple tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars) | Preserve primary section identity and native system presentation. |
| [Apple materials](https://developer.apple.com/design/human-interface-guidelines/materials), [layout](https://developer.apple.com/design/human-interface-guidelines/layout) and [adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass) | Audit navigation/content hierarchy and system accessibility adaptation; this is advisory, not approval to remove branded CSS materials. |
| [Fluent 2 tokens](https://fluent2.microsoft.design/design-tokens) | Semantic token roles and themes; future consolidation needs computed-output evidence. |
| [Windows touch](https://learn.microsoft.com/en-us/windows/apps/develop/input/touch-interactions) | Distinguish 40epx touchable from 44epx touch-optimized targets and account for keyboard occlusion. |
| [Android touch targets](https://support.google.com/accessibility/android/answer/7101858?hl=en) and [Android accessibility](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views) | Recommended 48dp effective target; enlarging a target must not overlap its neighbor. |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | Applicable AA contrast, text resizing, focus and non-gesture access gates. |

Official guidance is advisory; user-approved exceptions are product decisions.
Neither official references nor source inspection establish device acceptance.

## Quality gates for a later, approved UI implementation

Measure 44pt iOS, recommended 48dp Android and the appropriate Windows effective
targets, including hit slop and neighboring hit rectangles. CSS pixels are not a
claim of measured physical target compliance. Retain keyboard focus and ordinary
click/tap routes for every action; primary sections remain tap-only.

Exercise 12/13/14/16px text, compact/72px entries, ZH/EN/JA, 200% text scaling,
IME/focus switching, 320/375/393/430px, short heights, tablet/desktop sizes and all
three themes. Important content must remain readable, reachable and operable.
Assess applicable WCAG AA contrast: generally 4.5:1 ordinary text, 3:1 large text
and essential non-text states, with documented applicability/exceptions.

Test focus visibility, screen-reader names/order, reduced motion, high contrast
and reduced transparency. Browser media-query emulation is software evidence;
native UIKit/Android/Windows adaptation requires its own device/OS checks.

Future changes must name reused components/tokens, intended platform exceptions,
actual duplicate overrides removed, before/after visual evidence, commands and
failures/skips, and remaining physical gates. Small image baselines need human
review; screenshot similarity alone is not design compliance. Keep run-specific
evidence, investigation notes and implementation plans outside
the repository; only established rules belong here.
