Bilikara v0.8 Host desktop-shell design freeze
================================================

Status: frozen IA and responsive interaction contract
Scope: Host shell only; documentation and standalone wireframe, no production implementation
Baseline audited: work/v0.8.0 @ eac2f25b1744598b2122b35cb985678e686e6569

0. Freeze decisions at a glance
--------------------------------

Primary model: hybrid application shell.

  global toolbar
  +-----------------------------------------------------------------------+
  | rail | persistent Stage + playback surface | selected work workspace |
  |      | (one HostPlaybackSession media pair) | (width varies by goal) |
  +-----------------------------------------------------------------------+

* A persistent left tool rail selects Queue, Request / Discover, Random,
  or Session Users. It is the primary navigation.
* The Stage is shell infrastructure, not a workspace. Workspace changes must
  not move, replace, clone, hide-and-recreate, or re-own its video/audio pair.
* Queue owns History as a subview. Settings is a global drawer. QR and
  presentation/status summaries are toolbar popovers. Song detail is a
  contextual inspector owned by Request / Discover.
* Queue is compact. Search is deliberately wide. Random and Session Users are
  independently navigable even though they consume related data.
* The shell viewport does not use body/document scrolling. Every major list
  below has one named local scroll owner.
* “Local library” search means cached Gatcha source metadata, not downloaded
  media. “Followed users” currently appears to mean configured UID sources,
  not a proven live Bilibili-following list. These semantics remain visibly
  pending; the design does not manufacture missing contracts.

1. Product goals and non-goals
------------------------------

Goals

G1  Keep playback spatially and technically stable throughout a live session.
G2  Make Queue, requesting/discovery, Random, and Session Users one action away.
G3  Give each work context enough width and exactly one vertical scroll owner.
G4  Preserve current functionality and view state while removing page travel.
G5  Define coherent wide, medium, narrow, keyboard, and coarse-pointer behavior.
G6  Make destructive effects explicit and keep application/runtime files safe.
G7  Permit production migration in bounded slices with one HostPlaybackSession.

Non-goals

N1  No production DOM/CSS/JS, Python, Rust, Tauri, API, schema, or playback work.
N2  No temporary tabs or rearrangement of the current scrolling page.
N3  No generic component framework, Redux/store rewrite, or overlay manager.
N4  No new Shared/Local search semantics, cleanup API, or data-retention policy.
N5  No phone-Host optimization, Liquid Glass requirement, or brand replacement.
N6  No second player, background playback authority, or media ownership handoff.

2. Current product and source audit
-----------------------------------

Source facts

* static/index.html, static/app.js, static/styles.css and static/song-detail.*
  implement a warm, card-based Host whose document is currently the primary
  vertical scroll surface. At <=1120px its two-column layout becomes one
  column; at <=760px forms and headings stack, but body scrolling remains.
* The queue card is sticky at wide widths and internally scrolls playlist or
  history. Expanded search moves the existing search-card DOM into a modal;
  it does not create a second search implementation. Song detail is inserted
  into that modal and restores focus when closed.
* static/app.js state.hostPlaybackSession owns one exact video/audio pair.
  mountHostPlaybackSessionElements() creates one visible video and one hidden
  audio; replaceHostPlayerView() is used for accepted playback-program
  lifecycle changes. Same-program reconciliation reuses both elements.
* Rust runtime AppState is authoritative for current item, playlist, session
  users/history and player settings. Python is transport/persistence and
  retained I/O orchestration. Tauri owns windows, presentation and restart.
* The current search faces are local Gatcha metadata (/api/gatcha/search),
  configured-UID browsing (/api/gatcha/browse), and shared catalog search
  (/api/lark/search). Expanded search also exposes favorites, category,
  name/artist browse, and secret-gated review/blacklist tools.
* The current local Gatcha search joins configured UID video metadata and
  fetched favorite-list metadata. It does not index data/cache media files.
* Current overlays have independently evolved z-index values (roughly 120 to
  1200, with fullscreen/presentation at 9999). Escape closes several layers
  in one key event rather than a strict topmost-only stack. The final contract
  below normalizes roles, not implementation into a global manager.

Legend used in the inventory

  Frequency/urgency: VH live-critical; H frequent; M occasional; L rare.
  Life: A authoritative/persisted; P persisted preference/data; V local view;
        D local unsaved draft; T transient.
  Space: C compact; W wide; F near-full; H tall list; S short.
  Survive: Y survive workspace switch; R restore selection but close layer;
           N transient by design.
  Owners: AppState = Rust runtime authoritative state; GRepo = Rust runtime
          Gatcha repository; Host = Python HTTP/I/O adapter; UI = app.js/DOM;
          Tauri = desktop shell; Ext = Bilibili/Cloudflare/Feishu/GitHub.

2.3 Current responsive, scrolling and input audit

* Body/document is the main scroll owner. The wide queue adds a second local
  list scroll; expanded search and several modals add more local scroll roots.
* At <=1120px player, forms, Session Users, Search and Gatcha precede a static
  Queue vertically, forcing operators to travel away from the Stage.
* Hover/focus/pin works for the compact QR control. Most key actions are real
  buttons, but session-user and queue ordering still depend heavily on drag.
* Current Host information controls measure 40px; Remote controls measure
  44px in the browser baseline. Narrow/coarse Host must adopt 44px targets.
* Search modal prevents body scrolling. Selection lists use overscroll
  containment. Several animations lack a global reduced-motion override.

4. Navigation alternatives and decision
---------------------------------------

Alternative | result | reason
------------|--------|-------
Whole-screen vertical pagination | REJECT primary | Repeats page travel, separates operator from Stage, and gives no durable location for live contexts. It may remain only as motion-free scroll inside a workspace.
Full-view tabs | REJECT primary | A full-view swap implies that Stage is one page among peers or must be duplicated outside tabs. Search also needs contextual subnavigation beyond one flat row.
Persistent tool rail + workspace | ACCEPT foundation | Four peer goals stay one action away, selected state is explicit, and workspace width can vary independently of the Stage.
Overlay drawers | REJECT primary; ACCEPT responsive technique | Drawers are suitable for Settings and for wide workspaces when docking would starve the Stage. If every destination were a drawer, live context and selection would feel transient.
Hybrid | ACCEPT final | Persistent toolbar + rail + Stage; docked workspace where fit allows; overlay/near-full workspace and collapsible controls only when space requires it.

Why no top-tab primary navigation: the toolbar already carries global status
and quick actions, and horizontal labels would compete with now-playing status
at medium widths. Why no user-customizable OBS-like docks: v0.8 needs one
reviewable layout contract, not another layout-persistence product.

Placement rule: a toolbar control can navigate to a full Settings subsection,
but it must not duplicate that subsection’s complete form. A rail item selects
a work context; it does not execute playback or settings actions.

Rail side decision: LEFT, not implementation-dependent.

* Stage priority: the narrow rail consumes a fixed 64-68px at the leading edge;
  the Stage remains the central visual anchor while variable-width work opens
  from the trailing edge. The rail never overlays or divides the media surface.
* Current Queue placement: Queue stays in the familiar trailing/right work
  region instead of moving the live list across the Stage during migration.
* Reading order: in left-to-right locales the order is global navigation,
  Stage/transport, then the selected task. DOM and keyboard order match it.
* Search expansion: the 600-700px Request workspace expands/overlays from the
  right without hiding the left rail, so operators can always change context.
* Toolbar alignment: brand/Host identity anchors the left rail; QR,
  Presentation, health/update and Settings remain a distinct right-side global
  cluster rather than blending with workspace navigation.
* Pointer travel: a right rail would be closer to row actions, but would crowd
  the variable-width workspace edge and toolbar globals. The left rail accepts
  a longer mouse traverse in exchange for a stable target that never moves as
  workspace width changes; roving-arrow keyboard operation shortens this path.
* Touch/coarse pointer: the left edge stays exposed in Wide, Medium and Narrow,
  uses 44px-class targets, and requires neither hover nor an edge swipe. No
  right-hand assumption is baked into the v0.8 Host.

6. Search and source taxonomy contract
--------------------------------------

Decision

* “Shared catalog” and “Local library” are the final two-option segmented
  control labels inside Search. They are mutually exclusive scopes of the same query goal,
  not global tabs and not separate rail destinations.
* Each mode owns an independent query draft, submitted query, result set,
  loading/error state, selected result, pagination/cursor if the backend has
  one, and scrollTop. Switching restores the prior mode without a request.
  A Submit/Refresh action reruns it. The existing Shared and Local endpoints
  currently return bounded result arrays; the UI must not fake pagination.
* Discover is adjacent to Search because category/name/artist browse the same
  shared catalog but use browse intents rather than free-text scope switching.
* Sources distinguishes management from content search. Added UIDs and fetched
  Favorites are persistent source records. Search reads their cached metadata;
  Add UID, Refresh and Fetch collections alter the source set.
* Add UID exists once: Sources > Added UIDs. Random shows “Manage sources” as a
  navigation link to that location, never a second Add UID form.
* “Refresh videos” is an explicit action on Added UIDs. “Fetch collections” is
  an explicit action on Favorites, with preview/selection in a task sheet.
* Random remains independent: its user goal is drawing/configuring a pool, not
  finding or maintaining an owner.

Per-mode state contract

Field | Shared catalog | Local library | switch/restore rule
------|----------------|---------------|--------------------
query draft | independent text, placeholder “Search shared catalog” | independent text, placeholder “Search your local library” | keep each draft; never copy it across modes
submitted query | last explicitly submitted Shared query | last explicitly submitted Local query | restore without request; submit/refresh is explicit
results | Shared result array with its own empty state | cached UID/favorite metadata result array with its own empty state | never render one mode's array under the other label
pagination/cursor | current bounded <=80 result response; no cursor | current bounded result response; no cursor | retain a future cursor per mode only when its backend defines one; UI never fabricates paging
loading/error | independent status and last error | independent status and last error | switching does not cancel, relabel or leak the other status; a returning request updates only its origin mode
scroll position | result-list scrollTop | result-list scrollTop | save before switch and restore after the correct result DOM renders
selected song/detail | Shared selection plus source/freshness metadata | Local selection plus UID/favorite provenance | keep independently; close inspector on mode switch and reopen only for that mode's explicitly retained open state
filters/source selection | Shared table/browse filters when exposed | optional configured UID/favorite filter when backend exposes it | independent; absent controls remain absent rather than sharing a stale value
local draft state | unsubmitted query/filter edits | unsubmitted query/filter edits | survives workspace switches; may be discarded on reload under Section 10

Surface | records/content | actions | relationship to Search
--------|-----------------|---------|-----------------------
Added UIDs | explicitly configured UID profiles and cached owner videos | Add UID through preview/confirm; refresh available UID metadata; browse an owner's videos | Local library may search their cached metadata; it does not browse their directories
Favorites | fetched UID/folder collection records and cached items | preview a UID's folders, choose/fetch collections, browse folders/items | Local library may search fetched item metadata; it does not imply access to every authenticated favorite
Random pool references | inclusion/exclusion and weight references to UID/favorite sources | configure in Random; “Manage sources” navigates here | consumes the same records but does not duplicate source management

Quick Request remains the URL/BV/av entry with requester, tail/next and page
binding. Search remains query/result/detail. Sources remains management plus
hierarchical source-content browsing. Discover remains category/name/artist
browse of Shared catalog data; sharing a backend record does not merge these
user intents.

Not ready for implementation without a product/backend decision

S1  Whether “Followed users” should ever mean a live account-following list.
    Today the source proves only added/configured UIDs.
S2  Shared search pagination/cursor, ordering and freshness. Current contract is
    at most 80 combined Cloudflare/Feishu results; no client cursor exists.
S3  A physical media-cache search or local JSON import has no Host API/index
    contract and is absent from v0.8 IA until separately specified.
S4  Whether favorites are public-UID collections, authenticated-account
    collections, or both; current preview/fetch is UID/folder oriented.

Backend prerequisites are exact: new Shared paging needs a stable cursor,
ordering and freshness contract; physical media search/import needs a Rust-
authoritative index/query contract plus Host I/O boundaries; live Following
needs an authenticated relationship API and persisted source model; favorites
wording beyond current UID/folder fetch needs an authentication/ownership
contract. None is simulated by the wireframe or required to migrate current
bounded behavior.

These pending semantics do not block freezing placement: existing Local,
Shared, UID, Favorite and browse functions each have a final container. They
block only renaming or implementing capabilities the source does not provide.

7. Workspace width and scroll model
-----------------------------------

Preferred width is a workspace property, clamped to available shell width.
No user-resizable dock or persisted split width is required in v0.8.

Workspace | preferred wide width | medium behavior | narrow behavior | one vertical scroll owner
----------|----------------------|-----------------|-----------------|--------------------------
Queue | 400px (range 360-440) docked | 360px docked when Stage >=560px; otherwise 400px overlay | content-width workspace below mini-Stage | queue list OR history list; fixed header/current/footer
Request / Discover - Quick | 520px docked | 520px overlay if docking starves Stage | near-full content workspace | form has no scroll; binding sheet owns its option list
Request / Discover - Search/Discover | 640px (range 600-700) docked | 600px right overlay; never squeezed to Queue width | near-full content workspace | active results/browse content only; search controls fixed
Request / Discover - Sources | 620px docked | 580-620px right overlay | near-full content workspace | owner/folder/content list for the active source level
Random | 480px (range 440-520) docked | 420px docked if Stage >=560px | content-width workspace below mini-Stage | Random content only when configuration/result exceeds height; pool sheet owns its source list
Session Users | 460px (range 420-500) docked | 400px docked if Stage >=560px | content-width workspace below mini-Stage | users list; add/actions fixed
Settings | 480px drawer over workspace edge | 480px modal drawer from trailing edge | content-area sheet, not full OS window | settings sections
Song detail | 360px inspector beside results when total workspace >=960px | 380px overlay inside Request | near-full content sheet | detail body only when necessary

Scroll rules

* html, body and the shell root are height:100%, overflow:hidden.
* Wheel/touch deltas stay with the pointer’s active local owner. At its top or
  bottom, overscroll-behavior:contain prevents chaining into Stage or shell.
* Fixed local headers, segmented controls and action footers do not scroll.
* Avoid a vertically scrollable workspace surrounding a vertically scrollable
  list. When the list is the owner, the workspace grid is min-height:0 and
  overflow:hidden. Horizontal chip/tab rows may scroll horizontally only.
* A modal/sheet locks its background workspace scroll; on close, scrollTop and
  focus are restored. An overlay workspace prevents wheel/touch reaching the
  obscured Stage but does not pause or remount media.

Surface scroll ownership

Queue=queue/history list; Search=active result list; Sources=active owner/folder/
item list; Random=random content or its task sheet (never both); Session Users=
users list; Settings=settings sections; Song detail=detail body only if its
fixed header/actions cannot fit.

9. Playback-control and Stage contract
--------------------------------------

Mount invariant

* Exactly one session object and exact media pair from F01 exist. Shell Stage
  is created once. Workspace selection changes classes/attributes and local
  workspace visibility only.
* A workspace must never call mountHostPlaybackSessionElements(),
  replaceHostPlayerView(), claim/retire program, or media load methods.
* Responsive changes use CSS layout on the existing Stage. Presentation keeps
  its current explicit composition/lifecycle contract; it is not a hidden Host
  workspace player.

Always visible, including collapsed mode

1. Current title plus playing/paused/preparing/transition/cache-failure status.
2. Play/Pause (the discoverable equivalent of current player-surface toggle).
3. Next, with existing transition/confirmation behavior.
4. Mute state/action; the compact strip can show a numeric volume summary.
5. Fullscreen.
6. “Controls” trigger with aria-expanded and an explicit label/tooltip.

Collapsible extended surface

* Audio/vocal variants, complete AV-delay step/input/reset/lock controls,
  volume slider/value, and complete Key shift controls.
* It is inline below Stage in full mode and the same control surface in a
  bottom tray in collapsed mode. It is not duplicated in both places at once;
  one DOM subtree can be visually placed by shell CSS.

Trigger conditions

* Full only when measured Stage-control inline size >=720px AND shell content
  height >=620px AND no overlay intersects the deck.
* Otherwise collapsed. ResizeObserver/container-query style measurement is a
  future implementation detail; viewport/device-name branching is prohibited.
* Users may open/close the tray explicitly. It does not close on a fixed timer.

Keyboard/touch

* Tab reaches all controls in visual order. Space toggles playback only when
  Stage/player has focus and no text/select/range control is active. Escape
  closes the tray at its layer priority. No single-letter global shortcut runs
  while an input, textarea, select or contenteditable has focus.
* The orb is a button, 48px desktop / 56px coarse, supports Enter/Space, and is
  never hover-only. Swipe is optional enhancement, never the sole open/close.
* Opening/closing or switching responsive modes preserves player focus where
  possible, current playback time, media state, control values and authority.

10. State-preservation contract
-------------------------------

Category | examples | owner | workspace switch | reload/reconnect
---------|----------|-------|------------------|-----------------
Authoritative server state | current item, exact playback program/generation, queue/order/cache status, history, session users/order, AV delay/lock, volume/mute, Key, audio variant, cache policy, transition state | Rust AppState; Host transports/persists snapshots | always survives; no UI recomputation | restored only by existing AppState/persistence rules
Persistent source/account data | Gatcha cached videos, configured UIDs, favorite folders/items, pool config, BBDown credentials, Remote identity digests | Rust GRepo/Host filesystem/tool status | survives | existing persistence; retention changes require explicit contract
Persistent UI preferences | language, theme, update automatic/preview, remembered volume/mute, Tauri window geometry; legacy layout value is migration-only | current localStorage/Tauri config | survives except retired layout choice | current owners; old Basic/Full value is consumed/ignored as below
Local view state | selected workspace/subview/submode; each Search mode submitted query/results/cursor/scroll; source selection/level/scroll; selected song/detail; Gatcha result; Settings subsection | narrow Host shell view-state object plus existing feature state | survives and restores without refetch | session-memory only in first slice; default Queue after reload unless later approved
Local draft state | direct URL, requester selection, Search unsubmitted query per mode, Add UID, favorite selection, Gatcha config draft, session-user name/edit/reorder draft | owning form/view | survives ordinary workspace switch; validation reruns against authoritative snapshot | may be discarded on reload; no new persistence in v0.8 shell foundation
Transient layer state | hover QR, pinned QR, open Settings, tray, confirm, task modal, toast/banner timing, focus origin | local UI | close rules below; selected underlying content remains | never restored

Specific switch behavior

* Queue/History selection, scroll and row selection restore.
* Shared and Local query/result/loading-success/error/scroll states are
  independent. Switching modes or workspaces never silently reruns a request.
* Search/Discover/Sources each restore their last internal location. Selected
  song metadata is retained; its inspector closes when leaving Request and
  reopens on return only if it was explicitly open before leaving.
* Gatcha configuration draft/result and Session Users edit draft survive a
  normal switch. If the server snapshot invalidates a referenced UID/user,
  show an inline conflict and require resolution; do not overwrite authority.
* Settings remembers its subsection after close. Drawer-open is transient.
* No generic global store rewrite: add only shell selection and per-existing-
  view scroll/draft fields that current state does not already retain.

Legacy Host Basic / Full classification

Classification: REPLACED BY RESPONSIVE SHELL BEHAVIOR.

The current Basic flag hides bottom-grid and search-sub-card, while Full shows
them; it is a manual feature-visibility switch, not a distinct playback mode.
The frozen shell keeps every function reachable through workspaces and changes
Stage/workspace/control fit automatically. Therefore v0.8 removes the Host
Basic/Full selector rather than renaming it to an unproven Stage Focus mode.
During migration, stored “basic”, legacy “normal”, and “full” values all enter
the default responsive shell and the obsolete key may be removed only after
the new shell is live. This is migration compatibility, not a continuing
product mode. Remote layout behavior is outside this Host-only freeze.

11. Layers, focus and accessibility
-----------------------------------

Roles and priority (low to high)

Level | role | close/focus contract
------|------|---------------------
0 | toolbar, rail, Stage, docked workspace | normal document focus order; body does not scroll
1 | tooltip | noninteractive; hover is enhancement; also appears on focus; no focus move
2 | QR or Presentation popover | one at a time; hover/focus transient on fine pointer, click pins; outside/Escape closes; restore trigger when pinned
3 | medium/narrow workspace overlay | backdrop blocks background scroll; Escape returns to rail trigger; Stage media continues
4 | Settings drawer or song-detail inspector | one contextual drawer per region; close button and Escape; selection/subsection retained; focus returns to opener/selected result
5 | playback control tray | traps focus only when it covers most narrow content; Escape/outside explicit close returns orb; does not own playback
6 | task sheet (page binding, favorites, pool config, rating, developer) | modal focus trap; Cancel/backdrop rules preserve or explicitly discard drafts; focus returns to invoker
7 | confirmation | topmost interactive layer; destructive scope and consequence visible; Cancel default; Escape cancels; focus returns
8 | recovery/critical banner | below toolbar, live region; explicit action/dismiss; no surprise focus steal
9 | toast/status announcement | visual top layer but pointer-transparent except explicit action; aria-live; never traps/moves focus

Do not open a popover over another popover. Opening Settings closes an unpinned
popover and requests confirmation before discarding a dirty modal draft.

Escape handles exactly one highest-priority open layer per press:

  confirmation -> task sheet -> control tray -> inspector/Settings ->
  workspace overlay -> pinned QR/Presentation -> row menu -> no action

Recovery banners and toasts require their own controls and are not swept away
by an unrelated Escape. Fullscreen Escape remains browser/Tauri-owned first.

Navigation/accessibility contract

* Rail is one aria-label="Host workspaces" single-selection list (tabs or
  equivalent semantics). Selected destination exposes aria-selected or
  aria-current="page"; only the selected rail item is in the arrow-key roving
  tabindex. Up/Down move focus; Home/End jump; Enter/Space activates. Arrow
  focus does not change workspace until activation.
* Every icon has a visible label in v0.8 range and an accessible name. Badges
  append accessible text, not just color. Status never relies on color alone.
* Focus order follows Section 8. DOM order must remain stable when CSS changes
  placement. Workspace activation focuses its heading only when triggered by
  keyboard; pointer activation keeps predictable focus on the trigger.
* Song rows are buttons or contain named actions. The whole card may open
  detail, but nested request/menu actions have distinct names. Drag handles
  gain Move up/Move down alternatives and announce the new position.
* 40px minimum target on fine pointer, 44px on pointer:coarse. Touch has no
  hover dependency. QR click pins; every tooltip fact is also available via
  accessible name/description or adjacent text.
* prefers-reduced-motion removes flips, parallax and nonessential transforms;
  opacity may be immediate. Playback/status changes are not communicated only
  through animation.

12.2 Proposed user-facing actions

Symbols: Clear=remove/reset; Keep=unchanged; Archive=write current played record
then clear live state; Decide=product/backend decision required before exposure.

Effect | Start new karaoke session | Clear downloaded media | Reset Bilikara user data (with visible scope)
-------|----------------------------|------------------------|---------------------------------------------
Current item/queue | Clear after transition is stopped/confirmed | Keep | Clear
Current-session users | Clear | Keep | Clear
Current session history/backup | Archive then Clear | Keep | Clear
Played session archives | Keep new archive | Keep | Decide: retain by default vs explicit “also delete archives”
Media cache/artifacts/staging | Keep subject to normal cache policy | Clear | Clear
Configured UIDs/video metadata | Keep | Keep | Clear
Favorite folders/items/pool config | Keep | Keep | Clear
Bilibili/BBDown credentials | Keep | Keep | Decide: sign out vs retain; confirmation must say which
Remote identities | Keep | Keep | Clear/rotate
Language/theme/layout/update prefs | Keep | Keep | Clear to defaults
Window geometry | Keep | Keep | Clear to validated default
Logs | Keep | Keep | Decide: retain recent support logs vs delete
Update temporary files | Keep | Keep | Clear only verified temporary update directories
Downloaded tools | Keep | Keep | Keep; separate repair/uninstall action if ever added
Installed app/bundle/runtime | PROTECTED | PROTECTED | PROTECTED

Action wording and availability

* “Start new karaoke session” is clearer than “Clear current session”: its
  confirmation states that the live queue/users/history are archived/cleared
  while media, sources, accounts and preferences remain. This requires a new
  Rust AppState command/effect contract; do not emulate it in Python.
* “Clear downloaded media” is a narrowly scoped cache action. It may use the
  existing cache-runtime boundary after production review; confirmation says
  queued songs may need to download again. Active playback artifacts may remain
  physically retained until their existing reader/program ownership retires;
  the action still reports the logical cache clear, not internal directories.
  No confirmation or result exposes configured, alias or canonical path forms.
* “Reset Bilikara user data” must remain disabled/marked Contract pending until
  archive, credentials and log retention are decided and a Rust-authoritative
  semantic command plus validated Host file effects exist. Its destructive
  confirmation enumerates every selected category; an information tooltip is
  insufficient.
* Current /api/data/reset matches none of these labels cleanly: it clears cache,
  AppState runtime/player settings and Remote identities, preserves played
  archives/Gatcha cache/UID/favorites/localStorage, and may delete pool config.
  It must not be relabeled as a complete reset without contract work.

Protected in every action

* Installed executable, macOS .app bundle and Windows install destination.
* Packaged Rust native/runtime libraries and required Python/internal files.
* static application assets, vendor/_internal packaged dependencies.
* The Windows runtime/ directory as a directory; only explicitly classified
  children may be targeted after canonical path validation.
* APP_HOME/tools by default, including required BBDown/FFmpeg/yt-dlp/aria2c.
* Source tree/build files in development.

No cleanup uses APP_HOME, ROOT_DIR, runtime/, the app bundle or an unresolved
environment variable as a recursive deletion root.

13. Visual direction
--------------------

* Preserve bilikara’s warm cream/orange identity and friendly bilingual tone.
* Modernization comes from fixed chrome, hierarchy, local separators, variable
  workspace widths and fewer nested cards. Use 8-12px corner radii and compact
  density rather than a generic dark dashboard.
* Keep contrast at least WCAG AA for normal text/focus/status. Orange is an
  accent/selection signal, not the only status cue.
* Restrained shadow only distinguishes a drawer/popover. No required blur,
  glass, dark mode, stock illustration, or ornamental motion.

  Exclusions: no brand replacement, framework migration, generic overlay
  manager, decorative asset project, or backend/API work.

Dependency note: if Slice 1 cannot preserve exact media-element identity while
workspaces change, stop. Do not temporarily mount the player in both shells.
